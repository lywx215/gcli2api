# 双仓库方案第三方 Review 指南

状态：**Draft for Review**

## 1. Review目标

第三方应验证方案是否：

- 能让两个仓库独立开发和发布；
- 能兼容当前20台不同版本节点；
- 不泄漏或集中保存凭证；
- 不破坏现有gcli2api接口和SQLite；
- 能安全执行启停、Preview、额度和检测；
- 具备可执行的CI、灰度和回滚流程。

## 2. 严重级别

| 级别 | 定义 |
|---|---|
| P0 | 可造成凭证泄漏、数据损坏或全局不可用，必须阻断 |
| P1 | 可造成错误写操作、重大兼容问题或无法回滚，发布前必须解决 |
| P2 | 局部可靠性、可维护性或可观测性问题，应排期解决 |
| P3 | 文档、体验或优化建议，不阻断首版 |

## 3. 架构检查

- [ ] 两个仓库是否只通过HTTP协议耦合？
- [ ] 两仓库的`IMPLEMENTATION_ROADMAP.md`是否完全一致并预先定义MGMT-001至MGMT-010？
- [ ] 每个工作项是否都有依赖、范围、排除项、输入、验收、回滚和跨仓顺序？
- [ ] 是否禁止仅凭分支、Issue标题或阶段名开始实现，且未跳过路线图门禁？
- [ ] 职责是否清晰且没有重复实现业务规则？
- [ ] manager是否完全不接触节点SQLite和凭证文件？
- [ ] 单节点失败是否与其他节点隔离？
- [ ] manager是否使用独立MySQL 8，且应用服务保持无状态？
- [ ] manager MySQL是否只保存允许的元数据、快照、任务和审计，不保存完整凭证？
- [ ] 是否只建立一个manager数据库账号，由运行时、Alembic和人工排障共用？
- [ ] `SHOW GRANTS`是否证明该账号只访问`gcli2api_manager.*`，没有全局权限、
  `GRANT OPTION`或桌面端数据库权限？
- [ ] MySQL迁移、备份和恢复是否明确并实际验证？
- [ ] 是否只存在一个Web管理员，且没有注册、RBAC、角色、团队、租户或多用户管理？
- [ ] 桌面端是否保持独立，且不存在数据库直连、任务复用或同步预埋？
- [ ] new-api是否确实保持在本期范围之外？

## 4. 协议检查

- [ ] schema版本和应用版本是否分离？
- [ ] v1演进规则是否只允许向后兼容新增？
- [ ] capability是否足以控制UI和动作？
- [ ] Preview启用/关闭是否分开声明？
- [ ] 错误码、HTTP状态和retryable语义是否一致？
- [ ] Token未配置时是否默认关闭，且禁止空Token和其他密码回退？
- [ ] 所有时间字段是否统一为UTC ISO 8601或`null`？
- [ ] 凭证列表是否始终使用明确的分页外壳？
- [ ] 幂等和冲突行为是否明确？
- [ ] 缺失字段是否使用`null`而非0？
- [ ] 响应是否排除全部敏感字段？

## 5. 版本兼容检查

- [ ] 是否盘点20台现网明确版本或revision？
- [ ] 是否为每类响应建立脱敏Fixture？
- [ ] 能力判断是否以探测为主、版本号为辅？
- [ ] 未知版本是否默认只读？
- [ ] 是否定义完整支持、验证支持和维护支持边界？
- [ ] Legacy接口是否有回归测试？

## 6. 凭证操作检查

- [ ] 启停操作是否读取回节点真实状态？
- [ ] 永久禁用和删除是否二次确认？
- [ ] 删除超时后是否先查询再重试？
- [ ] Preview是否披露Google API副作用？
- [ ] 额度检测是否披露Token刷新和冷却同步？
- [ ] 主动检测是否限制并发并避免周期风控？
- [ ] 批量任务是否提供逐项结果？
- [ ] 批量任务是否同时定义批次和单项幂等，并避免重放成功项？

## 7. 安全检查

- [ ] `NODE_MANAGEMENT_TOKEN`是否与其他密码分离？
- [ ] manager是否加密保存节点Token？
- [ ] 浏览器是否永远拿不到节点Token？
- [ ] 日志和Fixture是否有自动敏感字段扫描？
- [ ] 跨域名重定向是否会剥离认证信息？
- [ ] 唯一管理员是否使用Argon2id密码哈希、安全Cookie会话、CSRF和登录限流？
- [ ] 审计是否覆盖全部写操作？

## 8. CI、发布和回滚检查

- [ ] MySQL是否完成空库迁移、上一版本升级和回滚或等价恢复验证？
- [ ] gcli2api的`dev8`是否确实从`origin/dev7@96736b1ea7e222c1a6a5f8e83ab95e0d4e1e3462`创建？
- [ ] 为默认分支启用接收workflow时，是否避免顺带合入未经Review的`dev8`业务提交？
- [ ] gcli2api是否发布固定SemVer镜像而非只用`latest`？
- [ ] manager是否测试最老现网版、Legacy、稳定版和RC？
- [ ] 跨仓库PR是否使用相同工作项编号？
- [ ] manager是否先于新版节点发布兼容支持？
- [ ] 是否采用2台、5台、剩余节点的灰度顺序？
- [ ] 是否明确数据库、镜像和配置回滚步骤？

### Web前端体验检查

- [ ] 是否使用React、Vite、TypeScript、Ant Design和ProComponents轻量骨架？
- [ ] 是否未复制完整Ant Design Pro、未引入Umi和无关示例模块？
- [ ] 是否提供亮色、暗色和跟随系统选项，并保存用户选择？
- [ ] 暗色是否保持语义层次和可读性，而非简单反色？
- [ ] 配色是否只参考Cockpit Tools的视觉层次，未复制其品牌资源、业务模块或未授权源码？
- [ ] 表格是否保持44px至48px目标行高，并固定关键操作列？
- [ ] 筛选、分页和批量选择是否操作清晰且能从URL恢复？
- [ ] 额度、Preview和测试是否使用清晰的抽屉或详情上下文？
- [ ] 永久禁用和删除是否独立于普通操作并二次确认？
- [ ] 未知字段、离线快照和不支持的capability是否正确呈现？

## 9. 自动交接与Token成本检查

- [ ] handoff schema是否把`execution_policy.mode`固定为`queue_only`？
- [ ] `max_automatic_runs`是否固定为`0`，且发送、接收工作流均再次校验？
- [ ] Actions是否只校验、投递和维护Issue，完全不调用Codex或其他模型？
- [ ] 是否禁止分钟级、周期性或常驻Codex轮询？
- [ ] 相同`delivery_id`是否只更新同一Issue，不产生重复任务？
- [ ] 跨仓库认证是否优先使用GitHub App短期令牌，PAT是否仅为可轮换回退？
- [ ] 投递失败是否在来源仓库留下可恢复Issue和Actions运行链接？
- [ ] GitHub或Codex账号更换后，交接队列是否仍保留且不依赖原任务会话？
- [ ] 如未来启用事件触发模型，是否经过单独Review，并具备一次性执行、预算、人工重试、
  禁止自动合并和禁止自动部署约束？

## 10. 必须演示的验收场景

1. 同时接入Modern、Legacy Current和Legacy Minimal节点。
2. 在单节点页面启用并禁用凭证，状态立即回读。
3. 对不支持Preview的节点正确隐藏按钮。
4. 对支持节点设置Preview并展示副作用及失败结果。
5. 查看额度并同步模型冷却，不泄漏Token。
6. 节点返回401、404、501和超时时正确降级。
7. 一个节点离线时其他19个节点继续可管理。
8. 批量任务部分失败后安全重试。
9. 扫描manager数据库、浏览器响应和日志，确认无完整凭证。
10. 创建一份handoff后，只生成或更新目标Issue，确认未发生任何模型调用。
11. 使用相同`delivery_id`重放，确认没有重复Issue；模拟投递失败并验证来源Issue可恢复。
12. 在空MySQL和上一版本数据库上执行迁移，并演示恢复步骤。
13. 演示节点列表、单节点凭证表格、筛选、批量操作和危险操作确认流程。
14. 使用运行时与Alembic共用的数据库账号执行`SHOW GRANTS`，证明权限仅限manager库。
15. 演示唯一管理员登录，并确认不存在注册、RBAC和多用户管理入口。
16. 从任一工作项追溯路线图定义、Issue状态、PR证据、handoff和发布门禁，确认范围未漂移。
