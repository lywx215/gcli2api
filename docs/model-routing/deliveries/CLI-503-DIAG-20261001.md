# CLI 503 专项诊断 — 2026-10-01

## 结论

已确定项目的 503 生成机制，但此前七次真实请求的原始上游错误码无法从现有记录恢复。不能把公开 503 直接认定为 Google 返回 503，也不能据此认定路由失败、凭证失效、许可不足或并发限流。

本轮获授权后完成两次串行真实模型诊断，没有再现 503：无工具请求返回原始 HTTP 200，但正文为空、结束原因为 `MALFORMED_FUNCTION_CALL`；带 Google Search 请求发生 `ReadTimeout`，项目公开状态为 504。两项都不算有效内容或联网成功。

## 已确认的错误改写

当前隔离服务的运行设置为：重试关闭、最大重试数 0、smart429 关闭、自动封禁关闭、封禁错误码列表 `[403]`。

| 实际条件 | 公开状态 | 已验证方式 |
|---|---:|---|
| 上游 429/500/503，关闭重试或预算耗尽 | 503 | 两种传输模式离线复现、完整三协议处理链复现 |
| 上游 403，错误列表 `[403]`，自动封禁关闭 | 503 | 两种传输模式及完整三协议处理链复现；封禁动作 0 |
| 无可用凭证 | 503 | 0 次上游调用的离线复现；legacy 500 经可信本地错误标记映射为公开 503 |
| 普通非超时连接异常 | 503 | 完整处理链注入 ConnectError 复现 |
| 已知 ReadTimeout | 504 | 离线及本轮真实请求验证 |

关键实现位置：

- `src/api/geminicli.py:206`：`_is_retryable_status` 把默认可重试码与封禁配置列表合并，未检查自动封禁开关。
- `src/api/geminicli.py:833`：非流式分支在不重试时统一构造 503；流式对应分支在第 455 行附近。
- `src/api/utils.py:188`：真正执行封禁前会检查封禁开关，所以关闭时并不会封禁；这不阻止外层此前进入“统一 503”分支。
- `config.py:187`：保存空列表 `[]` 会因真值判断回退默认 `[403]`，并不能通过简单保存空列表取消该改写。
- `src/router/model_api_errors.py:536`：已知超时保留可信 TIMEOUT 类型，安全边界呈现 504；不能把本轮真实 ReadTimeout 说成此前快速 503 的确定原因。

这两项配置/映射行为均存在于任务开始的 master 基线 `170d989f545218920bc84794472a0f234490694f`，不是本次模型路由新增。公开固定错误文案用于不泄漏内部名称和信息；应将该安全文案机制与先前已经发生的状态码合并分开分析。

## 授权后的真实复诊

第一次授权最多三次生成诊断，单次驱动在读取令牌后因过期检查停止：Google 调用 0，未刷新或写库。该时刻过期不能追认此前成功/失败请求的原因。

用户随后明确授权：最多三次 Google HTTPS 请求，允许一次仅内存 OAuth 刷新，再做无工具/带搜索两个非流式对照，不保存新令牌。

新版单次执行读取时访问令牌已有效，故无需 OAuth。最终总计 **2/3 次 Google HTTPS 请求：OAuth 0、生成 2**。独立进程只读 SQLite（URI mode=ro、query_only、SQL authorizer），统计、禁用和持久化动作使用内存替身；不向正在运行服务重新发送模型请求，不写凭证库，不改运行服务配置。

两次都请求同一个公开名称 `gemini-3.2-flash`，同一短问题要求定位 Google 官方搜索文档，区别仅为是否携带 `tools: [{"googleSearch": {}}]`。保留真实项目入站处理与 API/HTTP/响应安全路径；真实请求仅向固定官方 HTTPS origin 发送，TLS 验证开启，禁止环境代理、重定向、HTTP 重试及重复 case，统一硬预算限制为三次。

| 对照 | 原始上游观测 | 项目响应 | 内容/搜索判定 |
|---|---|---|---|
| 无工具非流式 | HTTP 200；139.125 秒到响应头；finishReason=`MALFORMED_FUNCTION_CALL`；正文为空、没有 grounding 字段 | HTTP 200；模型身份为客户端公开请求名 | 不通过；HTTP 200 与身份正确不足以证明内容有效 |
| 显式 googleSearch 非流式 | ReadTimeout；没有取得原始 HTTP、Google status/reason 或 finish/grounding | HTTP 504；可信错误分类 upstream/timeout；无模型身份字段 | 不通过；grounding 不可判定，不能声称“确认未搜索”或“元数据丢失” |

搜索请求没有保存精确实测总耗时。项目 API 向 HTTP 工厂传入 300 秒，但独立诊断的安全客户端替身设置读取时限为 180 秒；这也是复诊与运行实例的一个传输条件差异。两者都是配置，不能写成已测耗时 300 秒或 180 秒。该复诊可验证真实超时如何映射为 504，不是对原实例超时时限的完整重现。证据中的重复函数名来自 coroutine profile/resume，不是重复请求；真实 transport 计数严格为 2。

本轮没有抓到真实 403、429、500 或 503。因此离线已证实的映射机制不能被升级为“此前七次都因许可/额度失败”的结论。工具请求实际超时也不能追溯解释之前那些亚秒级 503。

## 修复建议（未实施）

1. 将“哪些错误可重试”与“哪些错误允许封禁”拆开，只有自动封禁开启时才处理对应配置；不要把关闭封禁后的 403 当成忙碌 503。
2. 重试结束后保留可信的原始状态码/错误类型，仍使用固定脱敏文案，不回传 Google 自由错误文本、上游名称或凭证。429 应能与本地无可用凭证、403 和容量 503 区分。
3. 明确定义空错误列表的配置语义，不因 `[]` 回退默认码而让设置失效。
4. 增加逐请求、仅内部可见的 allowlist 分类记录：原始状态、origin、reason 枚举、重试计数及本地筛选原因；不记录令牌、签名、密码或错误自由文本。
5. 保持“HTTP 成功”和“有效内容成功”分离；为正文空且 MALFORMED_FUNCTION_CALL、超时和 grounding 缺失分别补充验收。

仅打开重试不一定能解决权限拒绝或工具兼容性，也不能恢复已经丢失的历史错误记录。本轮只做分析及隔离测试，未修改业务实现。
